A project is the container where delivery happens: a roadmap, the people working
on it, chat, meetings, a resources library and the governance registers. There
are three ways to create one, and which you pick depends only on what you
already have in hand.

## Three ways to start

### Blank

Give the project a name and pick the workspace it belongs to. You land on an
empty roadmap, ready for its first epic. The system chat channels are there from
the first second, and the register pages your plan includes are already in the
sidebar, waiting to be filled.

Start here when the work is new and the shape of it is still in your head.

### From a roadmap you already have

Most work in Proyekto starts as a standalone roadmap — often before anyone has
agreed it is a project at all. Converting that roadmap gives it everything a
project has: a team, chat, meetings, a resources library and the registers.

> Converting adds to a roadmap. It never rebuilds it.

Every epic, feature and task stays exactly where it was, with its dates,
assignees and history intact. You are wrapping machinery around the plan, not
re-entering it. See [How roadmaps work](/docs/roadmaps-and-work/roadmaps-overview)
for what a roadmap is on its own.

### From a brief

If the work is already described in prose — a scope document, an email, a
written request — you can turn that brief into a project and let the AI
assistant draft the first roadmap from it. The assistant reads the brief,
proposes epics, features and tasks, and shows you the change before anything
lands; you approve it or throw it away. See
[Reviewing AI changes](/docs/ai-assistant/reviewing-changes).

Treat the draft as a first pass that saves you the blank page, not as a plan you
are stuck with. Editing it afterwards is ordinary roadmap work.

## What gets created either way

Whichever route you take, the same things are set up for you:

- **An access record making you the owner** — the top of the project access
  ladder. This is a separate record from your workspace membership, which is
  why it has to be created at all.
- **`#general`**, the system chat channel every project has. You can add more
  channels later; see [Project chat](/docs/chat-and-meetings/project-chat).
- **Default project settings**, including the permission defaults each role
  starts from.
- **The pages your plan includes.** Deliverables, change requests, risks and
  decisions appear on the plans that include them — see
  [Plans](/docs/workspaces-and-plans/plans).

One thing that is deliberately *not* created: access for anyone else. Being a
member of your workspace grants a colleague nothing inside a new project. You
add people explicitly, or by attaching a team — see
[Project access and roles](/docs/projects/access-and-roles).

## When you are at the project limit

Every plan sets how many projects a workspace can hold. When you have reached
that number, creating another one is blocked and Proyekto tells you so at the
point you try.

Nothing else changes. Reaching a limit only ever stops something *new*:

- Every project you already have stays open, readable and editable.
- Nothing is archived, hidden, downgraded or deleted.
- Roadmaps, chat history, files and register entries are all untouched.

To make room, you can move to a plan with a higher project allowance, or work
inside the projects you already have. [Limits and
usage](/docs/workspaces-and-plans/limits-and-usage) shows where you currently
stand against each counted limit.

## What the project name affects afterwards

The name is not decorative — it is the label people navigate by. It appears in
the project switcher, in search results, on rows in the
[Command center](/docs/roadmaps-and-work/command-center), in notifications, on
meeting invitations, and in activity entries.

That makes a vague name expensive later. "Website" tells nobody which website;
"Acme storefront rebuild" does. If the workspace runs work for several clients,
lead with the client.

Renaming is safe and takes effect everywhere at once — **Settings → General**
inside the project. Nothing is duplicated and no history is rewritten; the
project keeps every record it had under its previous name.
